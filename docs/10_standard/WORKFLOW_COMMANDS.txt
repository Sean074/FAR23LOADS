sloads — standard workflow commands (solo profile)
===================================================

Copy-paste command sequences for a release. This is a crib sheet, not the rule:
the authority is DEVELOPMENT_PROCESS.md (§0 solo profile; §1-§9 with a second
collaborator) and the closure tiers in CLAUDE.md. If this sheet and those pages
disagree, those pages win.

ONE branch per release, not one per item (2026-08-22). `dev/vX.Y.Z` is opened
off main once, every item of the milestone is committed directly onto it, and
main receives exactly one pull request at the end. There is no per-item branch,
no per-item PR, and no separate release/x.y.z branch.

Placeholders:  <X.Y.Z> release, e.g. 0.7.0    <N> issue number
               <slug> kebab-case item name    <Subject> commit subject in
               project style, e.g. "Short description"


---------------------------------------------------------------------------
A — ONCE PER RELEASE: open the milestone branch
---------------------------------------------------------------------------

# 1. Scope the milestone first: the issues that will be worked in it exist,
#    labelled (tier:* tag:* band:* kind:*) and on the milestone vX.Y.Z, and
#    their rows are in the priority table of docs/30_future/00_backlog.md.

# 2. Open and push the branch (preflight: on main, clean tree, branch is new).
scripts/solo_start.sh dev/v<X.Y.Z>

# One-time owner settings this model assumes on main (see DEVELOPMENT_PROCESS
# §0, "Branch protection"): PR required, required checks = the fast gate,
# "Require linear history" ON — so the milestone PR is REBASE-merged, which
# keeps one commit per item AND stays linear. Never squash: that collapses the
# whole milestone into one commit. No admin bypass is needed — nothing pushes
# to main directly.


---------------------------------------------------------------------------
B — PER ITEM, on the milestone branch (repeat until the milestone is empty)
---------------------------------------------------------------------------

# 1. Confirm where you are. Every item is worked here; never branch off it.
git status -sb                     # ## dev/v<X.Y.Z>...origin/dev/v<X.Y.Z>

# 2. Do the work, AND the closure artefacts, before closing:
#      tier S: changes/<slug>.<type>.md fragment + delete the item's backlog
#              row (your own row only — no renumbering)
#      tier M: tier S + the affected PROGRAM_SPEC.md / standard-doc section
#              + a one-paragraph changes/<slug>.history.md fragment
#      tier L: tier M + theory_sources.md citation + full-format history
#              fragment; design note agreed before code (in chat while solo)
#    The issue closes and the row leaves in THIS item's commit — that is what
#    keeps the backlog a live view of what is still open mid-milestone.

# 3. While iterating, run only the module's own test file. The full local gate
#    runs once, in step 4 (or by hand here if you prefer).
.venv/bin/python -m pytest tests/test_<module>.py

# 4. Close the item: gate (scaled to the change set), one commit, push, close
#    the issue with the branch SHA, then verify. --dry-run first shows the
#    sequence without doing it; --slug is REQUIRED (the branch names the
#    milestone, not the item).
scripts/solo_close.sh --slug <slug> <N> "<Subject>"      # closing issue #N
scripts/solo_close.sh --slug <slug> "<Subject>"          # no issue

# 5. The push runs the fast gate on dev/** — ADVISORY. Nothing waits on it and
#    it runs while you start the next item; just do not start the next item on
#    a red one. A re-push cancels the run in flight, so a burst of commits
#    leaves only the last one verified.
gh run list --branch dev/v<X.Y.Z> --limit 3

# 6. Next item: back to B1. No checkout, no pull, no branch churn.


---------------------------------------------------------------------------
C — ONCE PER RELEASE: cut it and land the milestone on main
---------------------------------------------------------------------------

# 1. The milestone is empty (band A has no rows left). Cut the release ON this
#    branch — RELEASE_PROCESS.md §4 steps 1-3: version bump, changelog build
#    (which rolls the history fragments), history roll. There is no
#    release/x.y.z branch.
.venv/bin/python scripts/build_changelog.py <X.Y.Z> --date $(date +%F)
.venv/bin/python scripts/backlog_issues.py check

# 2. One pull request into main, for the whole milestone. Its issues are
#    already closed, one per commit — so NO "Closes #N" in the body.
gh pr create --base main --head dev/v<X.Y.Z> --title "Release <X.Y.Z>" --body "…"

# 3. Wait for the fast gate, then REBASE-merge (never squash — squashing
#    would collapse the whole release into one commit and lose the
#    step-per-commit record; and never a merge commit — main enforces
#    linear history and refuses one). Rebase replays each item's commit
#    onto main individually, so the record survives and history stays
#    linear. It rewrites the SHAs, so delete the branch after.
gh pr checks --watch
gh pr merge --rebase

# 4. The merge push to main runs the full matrix (3.9/3.11 + coverage-
#    instrumented 3.12). This is the gate of record for the milestone; it is
#    fixed forward — red means the fix is the next item, not a revert.
git checkout main && git pull
gh run list --branch main --limit 3

# 5. Tag from main (RELEASE_PROCESS.md §4 step 4), then open the next
#    milestone branch: back to A.
git tag -a v<X.Y.Z> -m "Release v<X.Y.Z>" && git push origin v<X.Y.Z>


---------------------------------------------------------------------------
Recoveries
---------------------------------------------------------------------------

# solo_close.sh stops mid-sequence: it prints the recovery for the step it
# failed on — follow that, don't re-run blind.

# Gate failed: fix forward on the milestone branch. The gate runs BEFORE the
# commit, so a red gate has committed nothing — there is nothing to abort.

# The remote moved under you (a hotfix, or another machine):
git pull --rebase --autostash

# A critical defect in an ALREADY-RELEASED version, mid-milestone: that is the
# only thing that lands on main out of band (RELEASE_PROCESS.md §6). Afterwards
# the milestone branch must take main back, before the next item — by REBASE,
# never `git merge main`: a merge commit on the branch is what makes the
# milestone PR unmergeable at the end ("This branch must not contain merge
# commits"), and it is not visible until the cut. Corrected 2026-08-25.
git checkout dev/v<X.Y.Z> && git rebase main
# then re-check the three shared counters (SCHEMA_VERSION, Imperial digest,
# case-ID bands) — that merge is where they collide.
# A defect in UNRELEASED work is not a hotfix: it is the next item on the
# milestone branch.
